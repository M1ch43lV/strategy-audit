# Canonical corpus and execution profiles

The primary regime analysis uses one deduplicated canonical corpus. `original`
and `repaired` identify implementation provenance; they do not create separate
primary analysis worlds. An original and its repaired implementation can be
compared as a pair, but never count as two independent strategies in a ranking,
test, or cluster.

`execution_profiles.py` regenerates `EXECUTION_PROFILES.csv` from the same
alphabetical, first-class-name rule used by `corpus.py`. It prefers a measured
original, otherwise a documented Class 2 overlay, successful Class 1
environment repair, or successful FreqAI runtime result, in that order.

## Static profile fields

The classification intentionally separates four questions:

| Field | Meaning |
|---|---|
| `signal_capability` | Entry columns explicitly written by the source, irrespective of Freqtrade gates |
| `direction_capability` | Native effective direction after applying the published `can_short` value |
| `mode_support` | Conservative native mode selected from code, callbacks, path evidence, and completed runs |
| `run_profile` | Primary measurement stratum: `spot_long`, `futures_long`, `futures_short`, or `futures_long_short` |

An `enter_short` write with `can_short=False` or no declaration is recorded as
dormant short logic: `signal_capability=long_short`, but native
`direction_capability=long_only`. Enabling it would be a behavior-changing
variant. Conversely, `can_short=True` makes spot loading impossible but does not
prove that the code contains or reaches a short entry.

Static classification never claims that a particular window produced long or
short trades. The `observed_long_trades` and `observed_short_trades` fields stay
empty until a mode-correct runtime result supplies them.

The current source trees contain 900 unique class names, five more than the
published 895-row ledger. All 900 remain in the manifest; `ledger_present`
identifies the five additions rather than silently dropping them.

| `futures_long_short` | 61 |

Canonical provenance is 764 original implementations and 136 repaired
implementations: 53 Class 1 and 83 Class 2. Across the complete repair stack,
131 implementations are `strict_equivalent`, four are `output_equivalent`, one
is `behavior_changed`, and the 764 originals are `not_applicable`. These counts
come from `EXECUTION_PROFILES.csv`; they are not hard-coded analysis inputs.

Sixty-six rows require runtime or manual review. Fifty-eight of those expose
short-related source/configuration disagreement; four have no recognized entry
logic, and the remaining cases have mode evidence that needs confirmation.
Test and template candidates remain visible through `artifact_role`; they are
not silently deleted from the corpus.

## Runtime validation rule

Futures checks use `profile_futures_config.json` and the verified local Binance
USDT-M store. Across the eight requested pairs, the common native candle period
starts on 2020-02-04. Spot and futures results are separate run profiles because
funding, leverage, pair notation, and available history differ.

A smoke run can confirm that a strategy loads in a mode and can demonstrate
observed long or short trades. A zero count cannot prove that the corresponding
code path is impossible; static capability is therefore never overwritten by
one quiet test window.

All 101 native futures candidates were attempted. Eighty-four produced a valid
result: 40 produced both directions, 25 only long trades, six only short trades,
and 13 no trades in the test window. The latter still remain measured because a
zero-trade smoke window is not evidence that the static path is unreachable.
Seventeen remain failed and retain the exact reason in `PROFILE_SMOKE.json`.
They consist of 13 unresolved dependency/model-load cases, three incomplete or
missing author configurations, and one security block. They are not counted as
measured.

`PROFILE_CLASS1.json` records environment/configuration restorations separately
from source overlays. Five such restorations are applied successfully, 13 are
partial, and four are blocked (two missing author configurations, one missing
non-installable dependency, and one security block). The security-blocked
strategy is not executed because its source embeds a credential and invokes a
network client.

`PROFILE_REPAIRS.json` records 25 new Class 2 overlays generated by
`profile_repairs.py`. Twenty-two are strict compatibility equivalents and three
are output-equivalent signal/dtype repairs. Originals remain untouched. Several
strategies require both a Class 1 module-path restoration and a Class 2 current-
library compatibility overlay; both stages are exposed in the manifest rather
than collapsed into an ambiguous label.

`output_equivalent` is deliberately weaker than `strict_equivalent`: its proof
is file-specific and limited to trading decisions, not a claim that every
intermediate dataframe value or every future library version is identical.
All such rows remain a mandatory exclusion sensitivity.

Each smoke result stores both `canonical_sha256` and
`runtime_config_sha256`. Thus canonical code is not treated as a complete run
identity when author configuration changes the execution path. The runner uses
one fresh Freqtrade subprocess at a time; there is no shared mutable strategy
configuration between concurrent in-process runs.

Regime eligibility will be keyed by `strategy_id × run_profile`. Behavioral
clustering is performed within run profile first. A later cross-profile
meta-clustering may use standardized regime fingerprints, with provenance kept
as descriptive metadata and a sensitivity variable.
